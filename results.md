Query: **"What is the default `pool_size` for `Client.connect()`?"**
Strategy: `structured`. This is Q3 from above — the same query that missed
top-1 in section 2, shown here with full scores.

### Unfiltered (searches v2 + v3 together)

| Rank | Score | chunk_id | sdk_version | Text |
|---|---|---|---|---|
| 1 | 0.6874 | `structured:v2-client-connect:2` | **v2** | "`pool_size` sets the maximum number of concurrent TCP connections held open to the gateway." |
| 2 | 0.6576 | `structured:v2-client-connect:1` | **v2** | Parameters table (pool_size default **5**) |
| 3 | 0.6347 | `structured:v3-client-connect:2` | v3 | "...In SDK v2 the default `pool_size` was `5`; v3 doubled it to `10`..." |

**Top-1 is a v2 chunk.** If this were fed to generation ungrounded, a user
asking about the current SDK could be told `pool_size` defaults to `5` —
the stale v2 value — because the v2 prose chunk happens to score higher
than the v3 table row for this phrasing.

### Filtered (`sdk_version="v3"`)

| Rank | Score | chunk_id | sdk_version | Text |
|---|---|---|---|---|
| 1 | 0.6347 | `structured:v3-client-connect:2` | v3 | "...v3 doubled it to `10`..." |
| 2 | 0.6327 | `structured:v3-client-connect:1` | v3 | Parameters table (pool_size default **10**) |
| 3 | 0.4740 | `structured:v3-client-connect:0` | v3 | intro prose |

by `metadata["sdk_version"]` before truncating to `top_k` — so the filter
changes which chunk *wins*, not just which chunks get sliced off the end of
an already-decided top-5.

- Citation `[structured:v3-pagination:2]` resolves → yes. That chunk's text: "`limit` accepts any integer from `1` to `200`. Requesting a `limit` above `200` raises a `ValueError`..." Claim checks out.

**Q8: In the Client.send() code sample, how do you pass a custom retry_backoff_ms value when constructing the request?**

## 6. One retrieval that embarrassed me (Q6)

**Query:** "Is HTTP error code 429 (RATE_LIMITED) retryable according to the error reference?"

Both strategies rank the *correct* page (`v3-errors`, the codes table) at
rank 2–3, but **neither puts it at rank 1**. Top-1 for both is
`v3-client-send`'s "Notes" chunk — because `client_send.md` also mentions
"429 RATE_LIMITED" in its own prose ("If the broker returns a `429
RATE_LIMITED` response, `Client.send()` will honor `retry_backoff_ms`
before retrying..."). That sentence is semantically closer to the
literal question wording ("retryable", "429", "RATE_LIMITED") than the
terse table row `| 429 | RATE_LIMITED | yes | Too many requests...` is,
even though the table row is the actual source of truth.

**Diagnosis:** cross-referencing prose (one page casually mentioning
another page's fact) can out-rank the page that owns the fact, because
embedding similarity rewards natural-language overlap over terse
structured data. hit@5 hid this failure (the table shows up at rank 2–3,
so it's technically "found"); hit@1 caught it. This is a real limitation
neither chunker fixes — it's a cross-document semantic collision, not a
chunk-boundary problem, and it's why I don't fully trust hit@5 alone as
"solved."

## 7. Bonus: precision vs. completeness tension

**Query:** "How do I override the default retry_backoff_ms when calling Client.send() in code?" — top_k=5, both strategies, `sdk_version` unfiltered.

| | Baseline | Structured |
|---|---|---|
| Retrieved chunk_types | `mixed, mixed, mixed, mixed, mixed` | `table, prose, table, prose, prose` |
| Code chunk in top 5? | Yes (folded into a `mixed` chunk) | **No** — the actual code-fence chunk (`structured:v3-client-send:3`) ranks **9th** out of 39, outside any reasonable top-5 |
| Final answer | "...you can pass a different value for `retry_backoff_ms` parameter when calling the `Client.send()` method. For example:\n```python\nclient.send(message=\"order.created\", retry_backoff_ms=750)\n```" | "To override the default retry_backoff_ms when calling Client.send(), you can pass a keyword argument with your desired value. [structured:v3-client-send:1]" |

The structured chunker retrieves *more precisely on paper* — every one of
its top-5 chunks is directly about `retry_backoff_ms` (the table row, the
explanatory prose, the rate-limit note), a tighter set than baseline's
looser blobs. But because it also isolated the code fence into its own
chunk, and that chunk doesn't share much surface vocabulary with a
"how do I..." question, it drops out of the top 5 entirely. Baseline's
sloppier chunking accidentally keeps prose and code glued together, so the
code sample rides along "for free" even into a chunk that wasn't
specifically about code.

**The tension in two sentences:** precise, single-purpose chunks retrieve
cleanly for the fact they were built around, but a *task* question ("how do
I...") often needs two different chunk types (the parameter's definition
and a code sample) at once, and splitting them cleanly is exactly what
makes it possible for one to rank in and the other to rank out. Fixing this
isn't "chunk less precisely" — it's retrieving more diverse chunk_types per
page (e.g., always including the nearest code-example chunk when a
parameter-table chunk from the same section is in the top-k).

## 8. Which chunker ships, and why

**I'm keeping the structured chunker as the ingestion default**, with the
baseline logic still available for comparison. The deciding evidence isn't
the tied hit@5 (section 2) — it's what I could directly observe in the raw
chunk contents (not just metadata) by printing them in full:
`baseline:v3-client-send:0` opens a ` ```python` fence and is truncated
mid-call — `...response = client.send( message="order.created",` — with
**no closing ` ``` `** anywhere in that chunk. Read in isolation it is a
broken, unterminated code block missing every argument after `message`.
The word-overlap window happens to restart the fence from scratch in the
next chunk (`baseline:v3-client-send:1`: ` ```python from nimbus import
Client ...`), so the complete example does exist somewhere in the index —
but only by accident of the overlap size, not by design. The same thing
happens on `v3-errors.md` (`baseline:v3-errors:0` cuts off mid-`if
e.code`, unclosed fence). That is precisely the failure mode this
assignment was designed to catch, and the structured chunker never does
it — every table and every code fence in `sdk_index/structured.pkl` is a
single, complete, independently-retrievable chunk (verified by printing
every chunk in `sdk_index/structured.pkl` in full — see `chunk_structured`
in `sdk_ingest.py`). The cost is
real too (section 7's bonus case, and Q3's top-1 miss in section 2 are both
consequences of the same design: smaller, purer chunks compete more evenly
against near-duplicate content from other versions/sections, which is a
retrieval-ranking problem that the `sdk_version` filter — not the chunker —
is the correct lever for). Given the assignment's own goal ("does your
current chunker keep the default value attached to the method it belongs
to, or does it cut a code fence in half"), never splitting a table row or
a code fence is worth more than the ranking noise it introduces, which has
an independent fix (metadata filtering).
